1. 데이터시트 검색

학부연구인턴에서 USB 허브보드를 설계하면서 만든 도구입니다. 이 보드는 허브 컨트롤러로 CH334U를 사용합니다. 회로 설계에는 동작 전압, 핀 배치, 패키지 같은 정확한 사양이 필요합니다.

CH334/CH335는 4포트 USB 2.0 허브 컨트롤러 계열입니다.

  • 패키지: QSOP16 ~ LQFP48
  • 기능: TT 방식, 과전류 검출, 전원 제어, LED 표시
  • 품번 10종이 데이터시트 한 권(32쪽)에 함께 실려 있습니다

같은 표에서도 품번마다 값이 다릅니다. 패키지 표의 CH334R은 QSOP16이고 바로 아래 행의 CH334U는 QSOP28입니다.

언어모델은 근거가 부족하거나 다른 품번의 값이 섞여 있어도 그럴듯하게 답합니다(할루시네이션). 그래서 잘못된 근거로 답하지 않도록 검색기를 설계했습니다. 질문한 품번의 근거만 찾고 근거가 기준에 미치지 못하면 언어모델을 호출하지 않습니다.

IDEC 팀 운영 규격

IDEC 스마트 전자회로설계 챌린지 2인 팀 프로젝트(2026.11.11까지 진행 중)에서 발췌했습니다. 제 담당은 아날로그 회로, PCB, 시험 지그입니다.

이 폴더는 실행할 것이 없습니다. 이 README를 읽어 주시면 감사하겠습니다. 운영 규격 원문과 회로 설계 파일은 팀 저장소에 두고 이 폴더에는 README만 넣었습니다.

요약

작업 관리는 GitHub 저장소와 연동한 Plane으로 했습니다. 팀 운영 규격을 직접 작성해 Claude에 지시문으로 제공했고, Claude는 회의와 결정 사항을 이 규격에 맞춰 작업 항목과 설계 문서로 정리했습니다. 작업 목록은 스크립트로 Plane에 등록했고, 등록 전에 규격을 지켰는지 스크립트로 검사했습니다.

형식과 완료 기준을 규격으로 먼저 정해 두었기 때문에 작업 51개가 모두 같은 형식과 숫자로 된 완료 조건을 갖췄습니다.

항목 결과
작업 51개 (모듈 8개, 사이클 13개)
측정 가능한 완료 조건 280개 (작업당 평균 5.5개)
증빙 파일 경로 178개
설계 결정 기록 28건
진행 판정 시점 (Go/No-Go) 6곳

운영 규격의 핵심

  1. 작업종류 8종. 새 결론을 만드는 작업(RES)과 정리하는 작업(DOC)을 나눕니다. 기준은 "이 작업이 끝나면 프로젝트에 없던 결론이 생기는가" 한 문장입니다.
  2. 작업마다 네 항목. Goal, Work Items, Checklist, Deliverable을 씁니다. Checklist에는 "동작 확인", "정상 작동", "문제 없음"을 쓰지 않고 "리플 50 mVpp 이하"처럼 숫자로 씁니다. Deliverable은 파일 경로로 적습니다.
  3. 바뀌지 않는 작업 번호. [M모듈][C사이클 W작업][종류] 형식이고 W번호는 일정이 밀려도 바뀌지 않아 문서 사이의 참조가 깨지지 않습니다. 커밋 메시지에도 같은 번호를 붙여 회로가 바뀐 이유를 작업과 연결합니다.
  4. 설계 결정 기록. 결론, 근거, 검토한 대안, 재검토 조건을 함께 남깁니다.
  5. 되돌리기 어려운 시점. 부품 발주, PCB 발주처럼 되돌리기 어려운 6개 시점에는 진행 기준과 미충족 시 대응을 착수 전에 정합니다.

Plane으로 관리하는 방법

작업 하나하나를 Plane의 작업 항목으로 만들고 할 일과 완료 조건을 체크리스트로 관리합니다.

  1. 회의와 결정 사항을 Claude가 운영 규격에 맞춰 작업 항목으로 정리합니다
  2. 스크립트가 규격을 지켰는지 검사한 뒤 Plane API로 작업, 모듈 8개, 사이클 13개를 등록합니다
  3. 작업마다 상태를 Backlog, Todo, In Progress, Done 순서로 옮깁니다. 완료 조건을 모두 만족해야 Done이고 1인당 진행 중인 작업은 3개까지입니다
  4. 혼자 풀 수 없고 일정에 영향을 주는 문제는 Blocked로 올리고 원인과 필요한 조치를 코멘트로 남깁니다
  5. 커밋 메시지에 작업 번호를 붙여 GitHub의 변경 이력을 작업과 연결합니다

운영 규격에 적은 작업 항목의 작성 예시입니다. 할 일과 완료 조건을 체크리스트로 두고 완료 조건은 측정할 수 있는 숫자로 씁니다.

등록 전에 스크립트가 검사한 것. 작업종류가 8종 안인지, 완료 조건에 금지 표현이 있는지, 증빙이 파일 경로이고 파일명에 W번호가 있는지, 선행 작업 번호가 실제로 있는지, 번호 중복과 오타를 봤습니다. 51개가 확정된 뒤에는 등록 스크립트를 걷어내고 Plane 화면에서 운영하고 있어 스크립트는 이 폴더에 없습니다.

노션에서 쓰던 일정과 프로젝트 자료를 2026년 10월부터 제 PC의 HTML 페이지로 옮겨 관리하고 있습니다. 제출본에는 홈, 캘린더, IDEC 세 페이지와 중간고사 대비 강의정리를 넣었습니다.

요약

목적. 노션처럼 정해진 틀 안에서 화면을 맞추는 대신 제가 일하는 순서에 맞는 화면을 직접 만들기 위해서입니다. 프로젝트 파일에서 값을 바로 읽어 오는 화면처럼 기존 플랫폼으로는 만들 수 없던 것도 만들 수 있습니다.

추가 이점: 토큰. Claude로 관리할 때 주고받는 양이 적습니다. 같은 일을 노션 API(MCP)와 로컬 HTML로 각각 시키고 주고받은 글자 수를 비교했습니다 (2026.10.27, 처음 한 번 기준).

작업 로컬 HTML 노션 API
쓰기: 11/4 일정 하나 추가 호출 3번, 약 1,500자 호출 6번, 약 15,000자
읽기: 11/1~11/7 일정 목록 호출 1번, 약 500자 호출 3번, 약 8,000자
도구 설명 불러오기 없음 쓰기 약 13,000자, 읽기 약 22,000자 추가
  • 노션은 DB를 찾고 구조를 조회하는 데 대부분을 썼습니다. 일정이 수업 DB와 IDEC DB 두 곳에 나뉘어 있어 읽기도 두 번 조회해야 했습니다. 로컬은 두 일정을 한 파일에 합쳐 두어 한 번에 읽습니다.
  • DB 주소와 속성 이름을 이미 알고 쓰기만 반복하면 노션도 호출 한 번으로 끝나 차이가 줄어듭니다. 차이는 찾기, 구조 확인, 검증 단계에서 생깁니다.
  • 글자 수는 토큰 수와 대략 비례하는 비교용 지표입니다.

한계. 혼자 일정을 관리하는 데는 유리하지만 여러 사람이 함께 쓰는 데는 노션 같은 기존 플랫폼이 더 안정적입니다. 파일을 공유할 수는 있어도 화면 구조 자체가 제 작업 방식과 기호에 맞춰져 있어 다른 사람이 그대로 쓰기 어렵습니다. 동시 편집, 권한 관리, 백업처럼 기존 플랫폼이 기본으로 주는 기능도 직접 만들어야 합니다.

바로 보기 (약 3분)

index.html을 열어 주세요. 설치나 인터넷 연결 없이 열립니다. 아래 순서대로 3분 정도만 봐 주시면 감사하겠습니다. 페이지는 위쪽 검은 막대의 버튼으로 넘어갑니다.

01. 홈 (30초) 오늘과 내일 일정, 남은 일정 수, IDEC 부품과 네트 수를 한 화면에서 확인합니다.

02. 캘린더 (1분) 과목 칩(IDEC, 반공, 인공지능, 인반설)을 눌러 일정을 나눠 보고 월, 주, 일 보기를 바꿔 봐 주세요. 지난 미완료 수는 완료 체크가 원래 쓰던 브라우저에만 저장되어 생긴 것입니다.

03. IDEC (1분) 회로도 페이지의 줄(01_POWER 등)을 누르면 그 장에 들어갈 부품이 펼쳐집니다. ‘만들 것만’을 누르면 아직 만들어야 할 풋프린트만 남습니다. 부품 155개와 네트 128개는 넷리스트에서 바로 읽은 값입니다.

04. 강의정리 (30초) 과목 하나(예: 반도체공학 → 중간고사)를 열고 강의자료 번호를 눌러 정리와 문제 탭을 봐 주세요. ‘중간고사 연습’에서는 문제를 섞어 풀 수 있습니다.

직접 만든 이유

  1. 정해진 규격의 한계. 노션은 블록과 데이터베이스가 정한 틀 안에서만 화면을 구성합니다. 제 PC의 프로젝트 파일(넷리스트, 부품표)에서 값을 직접 읽어 오는 화면을 만들 수 없어 옮겨 적어야 했고 원본이 바뀌면 옮겨 적은 값과 어긋났습니다.
  2. 작업 순서에 맞춘 화면. 홈 한 장에서 오늘과 내일 할 일을 확인하고 IDEC 페이지에서는 회로도 장마다 들어갈 부품과 아직 만들어야 할 풋프린트를 바로 찾습니다.
  3. 구현 비용이 거의 사라졌습니다. 2026.10.07 하루 동안 노션 일정 가져오기, 휴대폰 캘린더용 .ics 내보내기, IDEC 부품 대응표 페이지를 만들었습니다. 구조와 규칙은 직접 정하고 구현은 Claude로 했습니다.
  4. 제 PC에서만 동작합니다. 데이터는 로컬 파일이고 페이지는 외부로 요청을 보내지 않습니다. 서버와 계정도 없습니다. 만드는 동안에는 Claude가 작업 폴더의 파일을 읽습니다. 따라서 여기서 말하는 보안은 “저장과 열람이 PC 안에서 끝나고 밖으로 내보낼 범위는 스크립트가 정한다”는 뜻입니다.

강의정리 (중간고사 대비)

2026-2학기 중간고사를 준비하며 직접 만든 페이지입니다. 예전에는 강의자료를 읽고 블로그에 글로 정리하는 정도였습니다. 이번 학기에는 공부에도 AI를 더 활용해 보려고 여러 방식을 시도하고 있고 이 페이지는 그중 처음 도입한 것입니다. 과목마다 강의자료 단위로 정리와 문제를 나누고 풀이를 접어 두었습니다. 문제를 섞어 푸는 연습 모드, 학습을 마친 구역을 표시하는 진도 표시, 페이지에서 바로 고치고 형광펜을 칠해 저장하는 편집 기능도 넣었습니다.

강의 슬라이드를 캡처한 그림은 제출본에서 빼고 그 자리에 그림 설명만 남겼습니다. 직접 실행한 실습 결과 그림은 그대로 두었습니다.

보완 계획

캘린더는 아직 기능이 부족합니다.

  • 화면에서 일정을 추가하거나 고칠 수 없습니다. 지금은 data.js를 고치거나 노션에서 가져옵니다
  • 반복 일정이 없습니다
  • 완료 체크가 브라우저에만 저장되어 다른 기기와 맞춰지지 않습니다
  • 알림은 휴대폰 캘린더(.ics 내보내기)에 맡기고 있습니다

기능은 요구 사항만 분명하면 AI로 대부분 구현할 수 있습니다. 그래서 앞으로는 디자인을 공부하려 합니다. 화면 구성의 원리와 좋은 사례를 익혀야 원하는 화면을 구체적으로 설명할 수 있고 생각한 것을 자유자재로 구현할 수 있습니다. AI에 모든 것을 맡기기보다 제가 먼저 알고 있는 지식으로 무엇을 만들지 정하고 AI를 최대한 활용하는 것이 목표입니다.
